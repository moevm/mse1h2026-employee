# Техническая документация проекта

## 1. Архитектура приложения

Проект функционирует на основе слоистой архитектуры (Layered Architecture), обеспечивающей разделение зон ответственности:
* **Presentation Layer (Уровень представления):** Отвечает за взаимодействие с пользователем через Telegram API. Построен на базе фреймворка Aiogram. Включает маршрутизаторы (routers), обработчики событий (handlers) и элементы пользовательского интерфейса (keyboards).
* **Business Logic Layer (Уровень бизнес-логики):** Инкапсулирует основные процессы системы (управление персоналом, задачами, отчетами, распределение ролей). Представлен сервисными классами в директории `services`.
* **Data Access Layer (Уровень доступа к данным):** Обеспечивает абстракцию над источником данных. Взаимодействие с Google Sheets API реализовано через единый клиентский класс, к которому обращаются сервисные модули.

```text
│
├── constants/                 # Модули строковых и структурных констант
│   ├── bot_constants.py       # Текстовые идентификаторы кнопок и callback-данных
│   ├── sheets_constants.py    # Идентификаторы столбцов базы данных
│   └── texts.py               # Системные сообщения и текстовые шаблоны
│
├── filters/                   # Пользовательские фильтры для маршрутизации
│   └── active_role.py         # Ограничение доступа к обработчикам на основе активной роли
│
├── states/                    # Классы машин состояний (FSM)
│   ├── lead.py                # Процессы руководителя
│   ├── manager_binding.py     # Процессы привязки сотрудников к руководителям
│   ├── task_report.py         # Процессы формирования отчетов
│   └── task_request.py        # Процессы инициации задач

│   └── role_menus.py          # Основные навигационные меню для различных ролей

│   └── task_request.py        # Обработка предложений по задачам
│
└── services/                  # Сервисные модули и классы бизнес-логики

    ├── google_sheets.py             # Базовый клиент интеграции с Google Sheets
    ├── manager_binding_service.py   # Логика закрепления подчиненных за руководителями
    ├── reminder_service.py          # Сервис отложенных и периодических уведомлений
    ├── reports_service.py           # Логика работы с отчетами о выполнении задач

```

## 3. Ключевые особенности системы

* **Организация хранения данных:** В качестве основной базы данных используется Google Sheets. Таблицы разделены на изолированные листы по предметным областям (Роли, Запросы ролей, Посещения, Задачи, Отчеты, Принятые задачи, Запросы руководителей). 
* **Модель авторизации и контроль доступа:** Идентификация пользователей осуществляется по Telegram ID. Система поддерживает наличие нескольких ролей у одного пользователя. Доступ к функциональным блокам предоставляется только после явного выбора пользователем активной роли на текущий сеанс. Права доступа проверяются на уровне маршрутизатора (router) при помощи фильтра `ActiveRoleFilter`.
* **Управление состояниями (FSM):** Для реализации многошаговых процессов (создание задач, написание отчетов) используется механизм конечных автоматов. Передача контекста между шагами осуществляется через внутреннюю память диспетчера Aiogram.
* **Жизненный цикл задач:** Задачи проходят строго определенный путь статусов (создана, в процессе, на рассмотрении, отменена, завершена). Архитектура предполагает интеграцию системы задач с подсистемой отчетов: задача считается окончательно принятой только после утверждения отчета руководителем, после чего происходит ее перенос в архивный лист таблицы.
* **Асинхронные фоновые процессы:** В системе интегрирован планировщик задач (`APScheduler`), который функционирует независимо от основного потока приема сообщений. Планировщик отвечает за автоматическую рассылку системных уведомлений (например, напоминания о начале и завершении рабочего дня).
* **Контроль рабочего времени:** Реализована подсистема учета рабочего времени (открытия и закрытия посещений). Логика системы запрещает смену активной роли или выход из сеанса при наличии незавершенной записи о рабочем дне.

## 4. Тестирование

Процесс тестирования системы построен на базе фреймворка `pytest`. Архитектура проекта предусматривает полное изолирование тестов от внешних API (Telegram и Google Sheets). 

Заглушки (mock-объекты) для инфраструктурных зависимостей, а также имитации системных сервисов располагаются в директории `tests/` в модулях `conftest.py` и `helpers.py`. Тестирование бизнес-логики и маршрутизаторов осуществляется путем передачи синтетических данных и объектов в изолированные функции-обработчики.
